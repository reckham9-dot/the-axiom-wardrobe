# AxiomWardrobe 0.9.6 — Paper API integration probe (не релиз)

**Что реально сделано:** отдельный Java-проект тестового плагина `AxiomRigProbe`, встроено независимое ядро 0.9.1, добавлены проверка ID ресурспака, спавн **одной** модели крыльев через `ItemDisplay` и пассажирское крепление к игроку. Старый AxiomWardrobe.jar **не меняется**. Покупки, SQL, SkinAPI, AuthMe, AxiomBridge не затрагиваются.

**Что не сделано:** в текущей среде отсутствуют Maven и загружаемый Paper API JAR, поэтому сборка **не прошла компиляцию с реальным Paper API**, а серверный JAR пока не сформирован. Пакет не содержит JAR для установки. Автоматический workflow компилирует проект с реальным Paper API в GitHub Actions (Temurin Java 25) или аналогичной среде с Maven и доступом к сети. Даже если компиляция успешна, настоящая привязка и геометрия должны пройти приёмку на Paper/клиенте 1.21.11.

## Как собрать (на машине с интернетом и Maven/Java 21)

```
mvn -B clean verify
./scripts/check-core.sh
```

При успехе `target/AxiomRigProbe-0.9.6-qa5.jar`. Тот же процесс описан в `.github/workflows/paper-api-build.yml`; после загрузки этого проекта в отдельный репозиторий GitHub Actions он собирает JAR в артефакт. **До успешного build не загружать файлы из проекта на рабочий Minecraft-сервер.**

## Установка после компиляции (только тестовый сервер/администратор)

1. Сохранить текущий рабочий AxiomWardrobe 0.8.0 без изменений. Отключить старый 3D-рендер: `cosmetics.custom-models-enabled=false`, `cosmetics.visual-preview-unsafe-enabled=false`. Skins и Bridge оставить работающими.
2. В ResourcePackManager должен находиться тестовый `AxiomWardrobe-Wings-Calibration-0.9.0-probe.zip`, содержащий `assets/theaxiom/items/wings_nether_probe.json`. Проверь загрузку этого ресурспака в клиенте отдельно на предмете.
3. Установить только **собранный с настоящим Paper API** `AxiomRigProbe-0.9.6-qa5.jar` в `plugins/` и запустить сервер. На первом запуске рендер выключен (`probe.enabled=false`).
4. Войти под администратором, дождаться загрузки ResourcePackManager и выполнить `/axiomrig status`. В строке `Last observed pack=` будет ID реально отправленного клиенту пакета. Это **не** UUID удалённой сессии magmaguy.com и не случайный UUID из другого сообщения.
5. В `plugins/AxiomRigProbe/config.yml` выставить `probe.required-pack-id` в найденный UUID и `probe.enabled=true`. Перезапустить сервер и зайти заново, чтобы событие `SUCCESSFULLY_LOADED` пришло после включения плагина.
6. В игре выполнить `/axiomrig show`. Убедиться в отсутствии ошибок и проверить **только одну пару крыльев**, в том числе со второго клиента. Для отключения — `/axiomrig hide`.
7. Если визуальное расположение неверно, использовать *только на тестовом сервере* `probe.x`, `probe.y`, `probe.z`, `probe.scale`. После настройки перезапустить тестовый сервер. При завершении испытания удалить только `AxiomRigProbe` и его сущности (плагин удаляет собственные ItemDisplay при отключении).

## Новое в 0.9.6

- Добавлена команда `/axiomrig tune <x> <y> <z> <scale>`: строго проверяет четыре числа, отклоняет NaN/Infinity и чрезмерные смещения, сохраняет значения в конфиг и пересоздаёт **только один** наш тестовый объект. Изменение работает без пересборки JAR и без изменения других плагинов.
- Исправлена диагностика для сервера с несколькими ресурспаками: событие о постороннем пакете больше не скрывает подтверждение загрузки требуемого набора.
- Добавлен регрессионный тест калибровки (1011 отдельных проверок). Путь `target/AxiomRigProbe-0.9.6-qa5.jar` и GitHub Actions обновлены.
- Обязательная граница безопасности: это **исходный интеграционный проект, не установочный JAR**. Настоящий API-зависимый JAR появится только после успешного Maven `verify` на GitHub Actions или машине с Paper API, затем нужен тест на сервере.

## Почему отдельный probe

После нескольких неудачных релизов недопустимо подменять работающий скин-движок неподтверждённой графикой. Этот проект не регистрирует `/wardrobe`, не читает `selections.yml`, не инициирует операции экономики, не устанавливает ресурспак. Он предназначен для подтверждения **одного** критического механизма: ресурспак принят + модель отображается на игроке + не отстаёт + удаляется без следов. Только после этого код может быть перенесён в единый AxiomWardrobe.jar.

## Дополнительная диагностика 0.9.6

Команда `/axiomrig inspect` из игры показывает раздельно: ID и статус ресурспака, наличие модели, привязку `getVehicle()==player`, выбранный `item_model`, режим ItemDisplay, позиции и число пассажиров. Это позволяет отличить успешное создание серверной сущности от реальной отрисовки клиента. Команда `/axiomrig show` больше не сообщает о монтаже без проверки результата `rig.attached(player)`; если объект не создался, выдаётся явное предупреждение.

Контроллер креплений предоставляет только read-only `attached(UUID)` для диагностики. Добавлены пять проверок отсутствия/присутствия дескриптора при спавне, перемещении, отказе и снятии объекта. Ресурсы, скины и сайт не менялись.

**Сборка настоящим Paper API и клиентские испытания НЕ выполнены.** Пока пользователь не создаст отдельный репозиторий и не запустит CI, пакет остаётся исходным тестовым проектом.

## Защита от устаревших событий ресурспака (0.9.6)

- При `FAILED_DOWNLOAD`, `DECLINED`, `DISCARDED`, `FAILED_RELOAD` и других неуспешных статусах **требуемого** пакета модель удаляется немедленно, а не остаётся висеть после остановки `tick()`.
- События ресурспака от предыдущей сессии игрока игнорируются при поздней доставке после переподключения.
- Эти защитные изменения не проверены на живом сервере: требуют сборки с Paper API и испытания.

## Дополнение 0.9.6: контроль фактического крепления

Обнаружен и устранён ложноположительный результат: если игрок не поворачивался, а другой плагин удалил тестового пассажира, старый контроллер продолжал считать объект прикреплённым. Теперь каждые 50 мс контроллер проверяет `ItemDisplay.isValid()`, мир, `display.getVehicle() == player` и наличие объекта в `player.getPassengers()`. Если какая-либо проверка не проходит, рендер отключается до явного следующего административного действия, без бесконечного создания сущностей. Регрессионный тест имитирует удаление пассажира без поворота и 1000 последующих игровых кадров.

Это только автономные тесты и статическая проверка адаптера; настоящий Paper API JAR и проверка игрового клиента ещё обязательны.
